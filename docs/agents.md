# Cascade — Agent Architecture, Guardrails & KPIs

> **TL;DR** — 4 designed agents + 1 optional foundation + N runtime instances generated by the Generator. Each agent has explicit guardrails and quantitative KPIs. Production rollout depends on shipping #3 + #4 together — never one without the other.

## Summary

- **Agent #1 — Q&A Agent (Reel chat)** · Layer 1 · Employee Mac · Sonnet 4.6 (escalate Opus 4.7) · ✅ Shipped
- **Agent #2 — Waste Detector** · Layer 2 · on-demand · Opus 4.7 · ✅ Built (LLM over #5 output only)
- **Agent #3 — Agent Generator** · Layer 2 · on-demand · Opus 4.7 · ✅ Built (typed validated spec)
- **Agent #4 — Deployment & Runtime Monitor** · Layer 2 · on-device · Sonnet 4.6 · ✅ Built (sandbox + lifecycle + anomaly + audit)
- **Agent #5 — Privacy Aggregator** · Layer 1 · Employee Mac · deterministic on-device · ✅ Built (allowlist + DP jitter + sensitive-app exclusion)

> Implementation note (2026-05-29): #2–#5 implemented in `cascade_agents.rs` (commands) + `cascade_llm.rs` (Anthropic client) + `cascade-schema` migration `0003_layer2_agents.sql`. #5 is deterministic (no LLM) so the privacy boundary is provable — the detector physically receives only `cascade_privacy_aggregates`, never raw OCR. The original "weekly batch / Local Llama" framing is the multi-employee production target; the single-Mac prototype runs #5 deterministically and #2/#3/#4 on the BYOK Anthropic key.

> N runtime fix-agents are the output of #3 — one template, N instances managed by #4.

## 1. Q&A Agent (Reel chat)

**Layer 1 · Employee Mac · Sonnet 4.6 default · Already shipped**

The chat panel in the Cascade Reel. Answers natural-language questions about the user's recorded day, citing real timestamps + apps.

### Guardrails

- **Hallucinated timestamps / fabricated events** — pipe prompt forces "every cited time must come from a real query result"; reject answers without citations when the question is recall-style.
- **Search loop blowup** — cap at 4 search calls + 20 results each per question.
- **Psychological judgments** — forbidden phrasing list: "you seemed unfocused", "you wasted time", etc.
- **Inferring during recording-off windows** — if queried range overlaps a pause, agent must state "recording was off between X and Y".
- **PII exfiltration** — pre-pass: redact passwords, credit cards, OAuth tokens from OCR before passing to Claude (regex + entropy scoring).
- **Content generation creep** — forbid "write the email for me" — stays retrospective. Refuse politely with rationale.
- **Off-topic / fishing** — refuse questions about other people's screens or system state outside captures.

### KPIs

- **Citation accuracy** ≥ 98% · every cited timestamp resolves to a real frame within 60s window
- **Hallucination rate** < 2% · human spot-check 50 answers/week vs captures
- **p95 latency** < 8s · OTel from question submit → answer streamed complete
- **Avg search calls per answer** 1.5 – 3 · < 1 = lazy; > 3.5 = over-fetching
- **Refusal-when-no-data rate** ≥ 90% on stress questions · synthetic test set
- **Re-ask rate (same intent within 5 min)** < 15% · embedding clustering on consecutive turns
- **Token cost per answer** $0.005 – $0.02 · Anthropic billing
- **Thumbs-up rate** ≥ 75% · needs UI (not built)

### Tuning dial

Sonnet 4.6 for routine. Escalate to Opus 4.7 when (a) question requires multi-step reasoning, (b) Sonnet confidence drops, (c) user retries.

## 2. Waste Detector

**Layer 2 · Server · Weekly batch · Opus 4.7 · Not built**

Reads aggregated team activity from #5, surfaces patterns of inefficiency for the manager.

### Guardrails

- **Targeting individuals** — minimum N=3 employees per flagged pattern. Single-person patterns are suppressed (only surfaced as anonymous trend).
- **First-week noise** — require baseline ≥ 14 days of data per employee before included in detection.
- **Surveillance creep** — detector receives only aggregator output (#5), never raw frames or OCR text.
- **Sensitive activity profiling** — hard whitelist: HR apps, banking, medical, legal — never analyzed even in aggregate.
- **Pattern flood** — cap at ≤ 6 patterns surfaced per manager per week (matches prototype's "six observations").
- **False urgency** — patterns tiered (info / suggest / urgent) — only urgent triggers manager notification.
- **Bias toward visible work** — balance metric: ratio of "communication overhead" vs "deep work fragmentation" flags should not skew either way.
- **Wellbeing signal** — if flagged pattern correlates with off-hours work growth, demote priority (don't reward overwork).

### KPIs

- **Pattern precision (manager-approves rate)** ≥ 70% · approvals / total surfaced
- **False-positive cost** < 30 min manager review time per rejected pattern · survey-based
- **Time saved per accepted pattern** ≥ 45 min/week per affected employee · measured 4 weeks post-cascade
- **Coverage proxy** · monthly "anything we missed?" survey — soft signal
- **Lead time** < 7 days from data accumulation to pattern surfacing · logged automatically
- **Tier calibration** < 5% of "urgent" patterns rejected by manager · tier-vs-action correlation
- **Wellbeing safeguard trip count** target 0 over-time concerns surfaced

### Tuning dial

Opus 4.7, temperature 0.2 (consistency > creativity). Single run per team per week — cost is rounding error.

## 3. Agent Generator

**Layer 2 · Server · On-demand · Opus 4.7 · Not built**

Given a waste pattern from #2, produces a structured agent specification. The output is a typed spec the Deployment Monitor (#4) consumes — NOT an executable until approved + tested.

### Spec output (every generated agent must include)

- **Task description** — one-line plain-English summary + one-paragraph rationale ("what this does and why it helps")
- **Required inputs** — declared schema: which Cascade events / external data the agent needs to read
- **Step-by-step workflow** — ordered, deterministic action list with explicit decision points
- **Tools needed** — declared from the manager-approved MCP whitelist only
- **Failure conditions** — what counts as a failed run (timeout, missing input, schema mismatch, tool error)
- **Approval points** — moments inside the workflow where human approval is required before proceeding (e.g., "before sending the email, ask user to confirm")
- **Rollback path** — what to do if the agent fires wrongly (undo, pause, escalate)
- **Estimated cost + time saved** — per-execution prediction (used for #4's KPI calibration)

### Guardrails

- **Spec completeness** — every spec field above is mandatory; reject incomplete specs at generation time.
- **Tool whitelist** — generated agents may declare tools only from the manager-approved MCP whitelist. No "exec shell" tool ever.
- **Deterministic workflow** — workflow steps must be linear or branching on schema-validated conditions, never "agent decides what to do next."
- **Approval-point density** — every state-mutating step (send, write, delete, transfer) must have an approval point on the first 3 runs.
- **Rollback path is required** — refuse to generate any agent that doesn't declare how to undo its own actions.
- **Estimated cost cap** — predicted per-execution cost > $0.10 → block. Cumulative weekly cost > $5 → block.
- **Description plain-English check** — readability score must pass (Flesch ≥ 60); no jargon-only descriptions.
- **No data exfiltration** — generated workflow cannot send Cascade event data to any URL outside the manager's declared server.
- **Cross-team isolation** — spec is generated for a specific team's waste pattern; cannot be re-cascaded to another team without re-generation.

### KPIs

- **Spec validation pass rate** ≥ 95% on first try · automated schema checks
- **Manager approval rate** ≥ 60% · lower means the generator doesn't understand manager taste — recalibrate exemplars
- **Token cost per generated spec** < $0.20 per generation
- **Time from waste-pattern → spec ready** < 30 seconds
- **Required-input schema validity** 100% · generated input schemas must match Cascade's actual event vocabulary
- **Rollback path completeness** 100% · enforced at generation time, but tracked because regression is dangerous
- **Description readability** Flesch ≥ 60 · automated

### Tuning dial

Opus 4.7, temperature 0.1 (deterministic). System prompt includes 3–5 high-quality reference specs as exemplars + the full MCP whitelist + the failure-condition catalog.

## 4. Deployment & Runtime Monitor

**Layer 2 · Client (employee Mac) + Server · Continuous · Sonnet 4.6 · Not built**

Owns the full lifecycle of a generated agent from manager approval through every execution. The agent that watches the other agents.

### Lifecycle stages

1. **Review** — present the spec to the employee in plain language (task description, what it'll do, what it needs, when it'll fire, how to undo). Employee can edit triggers, redact inputs, or decline.
2. **Sandbox test** — run the agent against synthetic or last-30-day historical data in a sandbox, with all external tool calls mocked. Surface what would have happened. Employee approves or rejects.
3. **Approval** — explicit employee + manager sign-off; both required. Audit-logged.
4. **First-N supervised runs** — every approval point is hard-required for the first 3 real executions. Then approval points become opt-in per spec.
5. **Steady-state monitoring** — every execution streamed to the activity feed; anomaly detection runs continuously.
6. **Rollback / pause** — single click in the employee app pauses; rollback restores the pre-action state for state-mutating tools (Gmail send → recall, Slack → delete, Notion → revert, etc., where APIs allow).
7. **Sunset** — agents with crash rate > 5% or employee-uninstall rate trends are auto-recommended for deprecation.

### Guardrails

- **Sandbox isolation** — sandbox test cannot reach external networks; all tool calls go through a mock layer with recorded fixtures.
- **Dual approval** — both employee AND manager must approve before the agent runs against real data. Manager-only approval is never sufficient.
- **First-3-runs supervision** — every approval point in the spec is treated as a hard stop for runs 1–3, regardless of spec defaults.
- **Real-time anomaly detection** — runs in parallel to every execution; flags scope creep (tool call outside declared list), output drift (output dissimilar to spec'd shape), excessive duration (> 3× predicted).
- **One-click pause** — single button in employee app pauses all agents. Cannot be disabled by manager.
- **Audit log immutable** — every action by every agent appended to an audit log the employee can export; cannot be edited or deleted by manager.
- **Reversibility enforced** — state-mutating actions must use APIs that support undo within a configurable window (default 5 min for sends, 60 min for writes). If not reversible, action requires per-execution approval, period.
- **Privacy boundary** — monitor receives only agent execution metadata (which tool fired when, success/fail, cost), never the data the agent processed.
- **Auto-recommend deprecation** — agent with crash rate > 5% over 7 days → recommend uninstall to employee + manager. Doesn't auto-uninstall (that's bossware in reverse).

### KPIs

- **Sandbox test pass rate** ≥ 80% · agents that pass sandbox should be deployable
- **Employee approval rate** ≥ 75% · lower = agents feel intrusive or unclear
- **Manager approval rate** ≥ 60% · lower = generator outputs don't match expectations
- **Dual approval lead time** < 48 hours from generation → both approvals · speed-to-value
- **First-3-runs zero-issue rate** ≥ 90% · if the first 3 monitored runs break, the spec was bad
- **Steady-state crash rate** < 2% per execution · core reliability
- **Anomaly detection precision** ≥ 80% · flagged anomalies that turn out to be real issues
- **Anomaly detection recall** ≥ 70% · real issues we caught vs total real issues
- **Time to pause** < 1 second from button click → all agents stopped · trust foundation
- **Rollback success rate** ≥ 95% on rollback-supported tools · if rollback fails, employee loses trust forever
- **14-day uninstall rate** < 15% · signal of bad agent fit
- **Predicted vs actual time saved (4 weeks)** ratio 0.7 – 1.3 · outside = recalibrate generator's prediction
- **Token cost per monitored execution** < $0.005 · monitor itself must be cheap; runs constantly

### Tuning dial

Sonnet 4.6, temperature 0.0 for anomaly detection (deterministic), temperature 0.3 for plain-English summaries shown to employees. Cheaper than Opus because it runs every execution — cost matters.

## 5. Privacy Aggregator

**Layer 1 · Employee Mac · Hourly · Local Llama 3.2 3B · Not built (recommended foundation)**

Sanitizes the employee's activity into shareable metrics before anything leaves the device. Foundation for the privacy promise — skip and the cascade exposes bossware risk.

### Guardrails

- **OCR text leakage** — output schema is allowlist only — fields: `app`, `duration_min`, `context_switches`, `category`. No `text`, no `window_title` past app boundary.
- **Small-N re-identification** — differential privacy: ε=1 noise added to counts < 10.
- **Sensitive app inclusion** — hard exclusion: banking, health, legal, dating, private browsing windows.
- **Hidden send** — employee can preview the aggregator's outbox before any send; daily diff shown.
- **Provider misuse** — aggregator can only send to manager's server URL declared at install time — no other URLs.

### KPIs

- **PII detection rate (audit)** — 0 leaks in random 100-payload sample / quarter
- **Local execution time** < 5s per hourly aggregation
- **Token cost** $0 · runs offline on Llama 3.2 3B
- **Employee opt-in rate** ≥ 80% in pilot
- **Server-acknowledged payload arrival rate** ≥ 99.5%

## Build sequence for Layer 2

Skipping #5 means #2 sees raw data → bossware lawsuit risk. **Do not skip.**

1. **Aggregator (#5)** on employee device + audit UI → foundation for trust
2. **Server: ingest aggregator data** + dashboard for manager (no LLM yet)
3. **Waste Detector (#2)** + manager surfacing UI
4. **Agent Generator (#3)** producing specs (NOT deploying yet — just generating into a holding area)
5. **Deployment & Runtime Monitor (#4)** — the entire approval/sandbox/monitor stack
6. **Iterate on KPIs**

Critical: **#3 and #4 must ship together.** A generator without a monitor = unsupervised deployment = the entire risk surface this architecture was designed to avoid.
